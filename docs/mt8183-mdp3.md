# MT8183 MDP3 (HW MM21→NV12) — investigation notes

**Status: OPEN / BLOCKED.** MDP3 M2M submits fine but never completes → the
V4L2 job times out and no frame is produced. Root cause is believed to be a
kernel **GCE/CMDQ** integration bug in the mainline `mtk-mdp3` path on this
SoC/kernel. It is **not required** for the bridge (see "Why it's low
priority"), but it is documented here so another agent can pick it up.

See also `AGENTS.md` and `docs/mt8183-notes.md` §2 / §6.

---

## TL;DR

- `/dev/video0` is `mtk-mdp3` (a stateful M2M device). It advertises
  `MM21` (tiled, 2-plane) on one queue and `NV12` on the other, so *in
  theory* it is the hardware MM21→NV12 de-tiler — the one thing the vcodec
  can't do (`/dev/video5` only outputs tiled MM21).
- `S_FMT` / `REQBUFS` / `QUERYBUF` / `mmap` / `QBUF` / `STREAMON` all
  succeed. **`DQBUF` never returns** (0/4 frames), and `dmesg` is silent.
- The GCE (CMDQ) IRQ is alive (`mtk_cmdq` fires) and the DT has the MDP3
  `gce-client-reg` / `gce-events`; the SCP firmware swap (cros v2.0.2798)
  changed nothing.
- Leading suspect: `cmdq_thread_irq_handler()` completes a task by comparing
  the **GCE's current PC** to the packet end
  (`curr_pa == task_end_pa - CMDQ_INST_SIZE`), but the MDP3 packet ends with
  `cmdq_pkt_eoc()` + a `cmdq_pkt_jump_rel()` **self-loop**, so the PC won't
  match → the task is never marked done → silent hang.
- **The SW de-tile in the bridge already solves the actual need** at
  ~1.4 ms/frame (~4% of one core @1080p30). This is a "nice to have", not a
  blocker.

---

## Why MDP3 was wanted

- `/dev/video5` (`mtk-vcodec-dec`, stateless) outputs **only MM21** (tiled),
  no NV12.
- The bridge currently de-tiles MM21→NV12 in **userspace** (`v4l2sl_mm21_detile`
  in `src/v4l2stateless_device.c`) — correct and cheap, but it is CPU work on
  every frame.
- MDP3 has a hardware tile engine; using it would offload that copy. MDP3 is
  also what ChromeOS uses for this conversion.

## Device / device-tree facts (this box)

- `/dev/video0` = `mtk-mdp3`; `/dev/video3` = mtk-jpeg-enc; `/dev/video4` =
  mtk-jpeg-enc; `/dev/video5` = mtk-vcodec-dec (stateless S264→MM21).
- Compatibles present: `mediatek,mt8183-mdp3-ccorr`, `…-rsz`, `…-wdma`,
  `rdma@1400b000`, `rdma@1400c000`, etc.
- Each MDP3 subdevice has `mediatek,gce-client-reg` and (most) have
  `mediatek,gce-events`, e.g. `rdma@1400b000` → `{0x81, 1, 0xb000, 0x1000}`.
  So the GCE client registration in the DTB looks correct.
- `mtk_cmdq` IRQ (MT_SYSIRQ 162) is active (~75k on CPU0).
- Modules: `mtk_mdp3` loaded.

## Reproduce

```sh
# tool is in the repo (see tools/v4l2_mdp3_stream.c)
cc -O2 -Wall -o tools/v4l2_mdp3_stream tools/v4l2_mdp3_stream.c
sudo dmesg -C
./tools/v4l2_mdp3_stream 1280 736 mm21
# observed: all S_FMT/REQBUFS/QUERYBUF/mmap/QBUF/STREAMON OK,
#           "result: 0/4 frames verified, 0 failed", dmesg empty
```

Expected (working): DQBUF returns 4 capture buffers with the de-tiled NV12.

## The completion path (from the sources)

Kernel sources are vendored under `drivers/media/platform/mediatek/mdp3/`
(v6.18.34). Also useful: `drivers/mailbox/mtk-cmdq-mailbox.c` (fetch it; not
vendored).

Submit (`mtk-mdp3-m2m.c` `mdp_m2m_device_run`):
1. `mdp_vpu_process()` — IPI to SCP.
2. `mdp_cmdq_send()` — build + flush the CMDQ packet.

Build (`mtk-mdp3-cmdq.c` `mdp_cmdq_prepare`), packet ends with:
```c
cmdq_pkt_eoc(&cmd->pkt);
cmdq_pkt_jump_rel(&cmd->pkt, CMDQ_INST_SIZE, mdp->cmdq_shift_pa[pp_idx]);
...
mdp->cmdq_clt[pp_idx]->client.rx_callback = mdp_handle_cmdq_callback;
```

Send (`mdp_cmdq_send`): `mbox_send_message(mdp->cmdq_clt[i]->chan, &cmd[i]->pkt)`.

Complete (expected chain, never observed):
```
GCE thread DONE IRQ
  -> cmdq_thread_irq_handler()          [mtk-cmdq-mailbox.c]
  -> cmdq_task_exec_done() -> mbox_chan_received_data()
  -> mdp_handle_cmdq_callback()         [mtk-mdp3-cmdq.c]
  -> queue_work(clock_wq, auto_release_work)
  -> mdp_auto_release_work() -> mdp_m2m_job_finish()
  -> v4l2_m2m_job_finish()              (DQBUF then returns)
```

## Ruled out

- **Firmware**: swapped `/lib/firmware/mediatek/mt8183/scp.img` to the
  ChromeOS build (`kukui_scp_v2.0.2798`, SHA `537748da…`) and rebooted —
  still 0/4. (Mainline backup: `scp.img.mainline-bak`.) → not (solely) the
  firmware.
- **DTB**: `gce-client-reg`/`gce-events` present; compatibles correct.
- **Dead GCE**: `mtk_cmdq` IRQ is firing.
- **Userspace plumbing**: S_FMT/REQBUFS/mmap/QBUF/STREAMON all succeed
  (see `tools/v4l2_mdp3_stream.c`).
- **Driver version**: hexdump0815 stb-cbm+ uses the same mainline v6.18 mdp3
  driver; its mt8183 patches are DTB/display-only, no mdp3/gce patches.

## Leading hypothesis

`cmdq_thread_irq_handler()` marks a task done **by PC**:
```c
gce_addr = readl(thread->base + CMDQ_THR_CURR_ADDR);
curr_pa  = cmdq_revert_gce_addr(gce_addr, cmdq->pdata);
...
if (!curr_task || curr_pa == task_end_pa - CMDQ_INST_SIZE) {
        cmdq_task_exec_done(task, 0);
```
The MDP3 packet ends with `EOC` + a **`jump_rel` self-loop** (keeps the GCE
thread parked so it can be resumed for the next frame). So at DONE-IRQ time
the GCE PC is likely inside that jump loop, **not** at
`task_end_pa - CMDQ_INST_SIZE` → `curr_task` is non-NULL but the equality
never holds → the task is never completed → `DQBUF` hangs forever, silently.

This could be a **mainline regression**: the packet shape (EOC + jump) and the
PC-equality check have to agree, and on this SoC/kernel they may not.

## Next steps / possible solutions (for the next agent)

Ranked, cheapest-first.

1. **Get visibility (highest value).** Build a kernel with
   `CONFIG_DYNAMIC_DEBUG` (and ideally ftrace). The stb kernel currently has
   neither. Enable dynamic debug for `mtk-cmdq-mailbox.c` and
   `mtk-mdp3-cmdq.c`, then rerun and watch:
   - `cmdq_irq_handler` / `cmdq_thread_irq_handler`: `irq_flag`,
     `gce_addr`/`curr_pa`, `task->pa_base`, `task->pkt->cmd_buf_size`,
     `task_end_pa`.
   - whether `cmdq_task_exec_done` is reached at all, and with what `sta`.
   - whether `mdp_handle_cmdq_callback` / `mdp_auto_release_work` /
     `mdp_m2m_job_finish` run.
   This single experiment distinguishes "GCE never fires DONE" from
   "fires but PC check fails" from "callback wiring broken".

2. **Confirm/extend the PC hypothesis.** If the logs show the DONE IRQ fires
   while `curr_pa` is in the jump loop, that confirms it. Candidate kernel
   fixes (test on a throwaway kernel):
   - Match the task by PC *range* (`curr_pa >= pa_base && < task_end_pa`)
     instead of the exact `end - INST_SIZE`, or
   - Check whether MDP3 should use `cmdq_pkt_eoc()` differently / not leave a
     jump self-loop at the packet end, or
   - See how `mtk-cmdq-mailbox.c` in the ChromeOS 5.10 tree handles this
     packet shape (the cros MDP3 works) and port the difference.

3. **Compare against ChromeOS.** ChromeOS (eMMC `/dev/mmcblk0p3`, kernel
   5.10) drives the same HW. Diff its `mtk-mdp3-*` and `mtk-cmdq-mailbox.c`
   against mainline v6.18. Likely the fastest route to the real fix.

4. **Check the GCE thread/subsys selection.** `mtk-mdp3-core.c`
   `mdp_cmdq_init` / the `mediatek,gce-client-reg` subsys (`0x81`, subsys 1/2)
   and `cmdq` shift/priority. Verify the thread the MDP3 packet is queued on
   is the one whose DONE IRQ the mailbox waits for (thread/`irq_mask`).

5. **Rule out the test tool.** Re-drive MDP3 with a known-good client
   (`media-ctl`/`v4l2-ctl` with the media graph, or a tiny m2m program) to be
   sure `tools/v4l2_mdp3_stream.c` isn't mis-queueing. (Low probability — the
   tool already matches the bridge's working M2M sequence.)

6. **SCP/VPU side.** `mdp_vpu_process()` does succeed, but confirm the SCP
   actually runs the tile-engine job (the SCP is the same core the vcodec
   uses for H.264 — that path works, so the SCP is generally healthy).

7. **Upstream search.** Check linux-media / `lore.kernel.org` for
   `mtk-mdp3` M2M fixes after v6.18 (e.g. CMDQ packet/IRQ handling, MT8183
   M2M). A one-line backport may be the whole fix.

## Workarounds if it can't be fixed

- **Keep the SW de-tile** (current): `v4l2sl_mm21_detile` —
  ~1.4 ms/frame @1080p (~4% of one core @30fps). This is the only real cost
  MDP3 would remove.
- If the de-tile CPU ever matters (battery/power), revisit MDP3; until then
  it is not worth the kernel effort.
